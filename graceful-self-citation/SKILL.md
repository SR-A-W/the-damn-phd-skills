# Graceful Self-Citation — 优雅自引工作流

## 调用形态

```
/graceful-self-citation <链接> [可选:比例/上限/备注]
```
- `<链接>` 可以是:**Google Scholar 个人主页**(引这个人的文章,合理范围内尽量多)、**单篇文章链接**(arXiv / OpenReview / anthology / DOI,只引这一篇)、或多个链接混合。
- 无链接调用 → 向用户要链接,不要猜。
- 链接类型自动判别:Scholar `citations?user=` → 人物模式(走完整分诊);单篇 → 跳过 Phase 1 的清单抓取,直接对这一篇做 Phase 2 的真窄家测试。

## 连续性(增量模式,默认行为)

**本 skill 不是一次性的。** 每次调用都必须先探测"之前是否已经跑过",跑过则**在既有成果上继续加**,绝不另起炉灶:

1. **探测既有宿主**:在 appendix 源码里找上次建的宿主章节(优先认 `% GSC-LEDGER` 标记块,其次认 "Broader Impact / Future Applications" 类标题)。找到 → 本次只做**增量**:新文章分诊后并入**既有主题子块**;确需新子块才新建;宿主章节位置、既有措辞、已转正的黑字**一概不动**(除非新引用要求在某句末尾加键)。
2. **台账(ledger)**:宿主章节源码顶部维护一个注释块,每次调用追加一行,形如:
   ```
   % GSC-LEDGER: <日期> | 来源=<链接或人名> | 新增 self=<n1> anchor=<n2> | 累计 self=<S> anchor=<A> | keys=<k1,k2,...>
   ```
   这是跨 session 的记忆载体:**自引/锚点的全局比例按累计值算**,不是按本次算。新一轮加了 3 篇自引而累计比例跌破线,就要补锚点或提醒用户。
3. **查重**:新候选先对全 bib 已有 key 去重(同 arXiv id / 归一化标题);已引的文章直接跳过并在报告里注明"此前已引于第 X 处"。
4. **不重复审阅已定稿内容**:审阅色只上**本次新增**的文字;上一轮已转黑的部分绝不重新变色。
5. 若探测到宿主章节存在但无 ledger(别人手工建的),先反推一份 ledger(数清现有 self/anchor)再增量。

把"要引的文章清单"(自家论文、导师/朋友/同组的论文)织入一篇 CS 论文,使每条引用都**读起来像本来就该在那里**,而不是塞进去的。核心哲学一句话:

> **Seamless ≠ 措辞技巧。Seamless = 真实的主题契合 + 诚实的行文。**
> 一条引用被挂在它不支持的句子上,任何措辞都救不了;只有给它真实的存在理由(或者不引)。

> **总纲——作用域纪律**:一个「通过/查过」所提供的保证,上限是它的作用域。每报告一项结论,
> 同时说明这项检查看不见什么(例:"按 Scholar Profile 统计"看不见 Profile 未收录的合作论文;
> "正文搜索零命中"看不见附录)。口径没写明的统计和"查过了"的断言,都要先补上口径再交付。

## 输入

- 一个或多个 Google Scholar 个人主页链接 / OpenReview 链接 / 论文清单
- 目标论文的 LaTeX 仓库路径
- 可选:用户指定的自引:外部锚点比例(默认**至少 1:1**)、数量上限

## 总流程(7 个 Phase,每个都有硬性验收)

### Phase 0 — 读懂宿主论文
0. **先走"连续性探测"**(见上):有既有宿主 → 增量路径,跳过本 Phase 的第 2、3 步。
1. 通读目标论文的正文与 appendix,列出:已有的 related-work 簇、已有 bib 全部 key(重点:**已在 bib 但未被引用的高引条目是免费锚点**,优先复用)。
2. 确定**宿主段落**。两个合法的家:
   - 正文 Related Work(保持精瘦,不动为妙);
   - **Appendix 的 "Broader Impact and Future Applications" 类章节**(首选)。"未来应用/展望"框架天然欢迎向外指的引用——读者*预期*这里有引用,不觉突兀。
   - 反过来也成立:**考察同作者/团队先例论文的既有挂载方案时,必须优先检查其附录的对应章节**,正文搜索可能完全找不到(实测:先例论文正文全段零命中,附录 4 段内命中全部 12 篇候选的挂载句——只搜正文会误判为"只列不引")。
3. **宿主段落必须是论文本来就需要的**。先问:这篇论文有什么真实的、承重的关切(效率?泛化?部署?)能自然吸入这批文献?有 → 以它为骨架;没有 → 如实告诉用户"这批文章没有诚实的家",让用户决定。

### Phase 1 — 抓取候选清单
1. `WebFetch` Scholar 主页(按日期排序的 list_works 页),提取:标题 / venue / 年份 / 引用数。Scholar 常被墙:退路依次为 WebSearch 标题、arXiv author query、用户直接贴截图(截图里的**缩写作者名只能当线索,不能进 bib**,见 Phase 5)。
2. 对每篇标注 arXiv id / OpenReview id / anthology id(后续核验用)。

### Phase 2 — 契合度三档分诊(整个 skill 的灵魂)
对每篇候选做 "**真窄家测试**":这篇文章**具体覆盖**宿主论文的哪个细分子话题?
- 先把宿主论文可挂引用的位置拆成**子话题簇**(从论文内容推导,不是套模板;常见:量化 / 剪枝 / KV-cache / 稀疏专家 / 蒸馏 / test-time compute / agent 记忆 / agent 评测 / skill 生态 / serving 延迟……)。
- **强契合**:候选文的核心贡献正好落在某个已有簇 → 直接进该簇的 `\citep`。
- **中契合**:需要**新写一个从句/子块**才能安放,且要**另配一个公认锚点**撑住 → 列出代价,让用户选。
- **不契合**:没有诚实的家 → **明确建议不引**。硬塞就是审稿人一眼识破的 padding;"把不相关文章藏在好文章堆里"不是本 skill 教的稀释,是本 skill 明令禁止的走私。
- **odd-fit 特例**(如领域跨度大的综述):去**读它的 taxonomy 确认**它真覆盖某个窄子话题(verify, don't assume),然后**只**挂那一个窄家、与该簇的公认方法**同一个 `\citep{}`** ——既真实又视觉降权。
- **判覆盖范围不能只看标题**:必须读摘要/目录/关键段落确认。综述类文献的标题与实际覆盖范围经常不一致——可能更窄,也可能更宽(实测两次方向相反:一篇标题带强领域标签的效率综述,读了内容才发现覆盖架构/数据/训练/推理四大类,与宿主论文精确对应,初判"完全不同领域"被反转;另一篇看似讨论模型能力的高引综述,读完确认核心是任务选型指南、确实不契合——判断维持,但过程证明必须先读再下结论)。
- **每人候选池里引用数最高的前 3 篇,无论初步印象如何,必须做深度内容核实**(读摘要,不能只读标题),并在报告里逐一说明判断依据。高引文献即使最终判定不契合,也要展示核实过程,不能一句"领域不同"带过(实测:两位学者各自引用量最高的文章都在初次分诊时被标题粗筛否决,其中一篇属误判,靠用户主动追问才第二次核实)。

产出:三档清单表(篇名/venue/拟挂位置/所需代价)→ **交用户拍板,绝不擅自全加**。用户砍掉的档,连同为其新设的从句和锚点一起撤干净。

### Phase 3 — 锚点稀释(比例是硬指标)
- **每个簇至少配一个公认的、venue 正式发表的高引锚点**;自引**永不单独成 `\citep`**(唯一许可例外:该自引描述一个确实没有外部锚点的独特设定——要在报告里显式声明这个例外)。
- 全局比例:自引(含同组/同机构合作者的文章,用户通常把这些也算"自己人"):外部锚点 **≥ 用户指定比例(默认 1:1)**。
- 锚点选择顺序:① **已有 bib 里的未引条目**(零成本);② 各子领域的教科书级论文(选 venue 版:ICLR/NeurIPS/ICML/ACL/MLSys/TMLR/JMLR)。
- 已知改名坑:有的论文 arXiv 名与 venue 名不同(例:GPTQ 的 ICLR 2023 正式版叫 **OPTQ**)——DBLP 按 arXiv 标题查不到 venue 版时,先查作者的 venue 记录再下"没有正式版"的结论。

### Phase 4 — 行文规则(概念先行)
- 每句**先陈述概念,句末从句挂引用**:`…reduced via post-training quantization~\citep{A, B}` ;**禁止** "We cite X, which proposes Y"。
- 按子话题**分从句群组**引用,一句自然的话可以携带多个 `\citep` 而不成 citation dump。
- 结构:宿主章节拆成 3-5 个**主题子块**(`\paragraph{}`,不进目录),每块 2-4 句。两大段无结构地摆引用会被用户/审稿人打回("看着比较水")。
- **不夸大被引工作**:按它实际做的描述;把窄综述吹成通用综述本身就是红旗。
- 位置:宿主章节放 **Appendix 的最末尾**;插入时警惕**层级吞并**(在 `\subsubsection` 之前插 `\subsection` 会把后者吸成自己的下级——插入后用 `.aux` 核对全部编号,不能只看源码)。

### Phase 5 — bib 零幻觉纪律(不可协商)
- **每条 bib 都从权威源拉**:arXiv `/abs` 页的 `citation_author` meta 标签(注意:`export.arxiv.org` API 对很新的 id 可能返回空——**API 查不到 ≠ 不存在**,以 /abs 页为准)、DBLP、ACL Anthology、OpenReview API、期刊官网。**绝不手写、绝不信搜索摘要、绝不从 Scholar 截图抄缩写名**。
- 一条也编不出来时**停下要材料**,宁可阻塞也不 fabricate——"零幻觉引用"是一票否决项。(实战正例:一条候选在 Scholar 之外的所有权威源都查不到、也无 arXiv id,如实报告"查不到"这个中间状态,用户看后直接决定不引——若图省事按 Scholar 的模糊信息编一个 id,就是本 skill 存在的意义本要防止的那类错误。诚实的"查不到"本身就是合格交付。)
- **逐字措辞取证同守零幻觉**:凡需要根据某文献的**逐字措辞**下判断(典型:考察先例论文对某候选的挂载句是"诚实标注"还是"藏进好文章堆")时,必须 `curl` 原始 PDF + `pdftotext`(或等效可验证抽取),**不得依赖 WebFetch/搜索引擎给出的"引用"**——这类工具被要求"逐字引用"时会生成看似合理但不存在的句子(实测:同一句话 WebFetch 版查无出处、结论"诚实标注";pdftotext 版与原文逐字一致、结论正好相反,错误结论已发进决策链后才靠亲自复核撤回)。
- preprint 一律升级到 venue 正式版(存在的话)。**升级时必须重新从该 venue 的官方记录(Anthology/DBLP/PMLR 等)完整拉取作者表,逐位与预印本比对,不得复用预印本的作者表只换 venue 字段**——作者表漂移不只是顺序微调,实测三例形态各异:排位第 5 变并列一作(贡献认定变了)、一作更换+某作者从名单消失(人员增删)、9 位变 7 位;没有规律可循,无法凭经验判断要不要重拉。只换 venue 字段会在"已是正式版"的表象下留一条作者信息仍是旧版的引用——更隐蔽的引用错误。
- **标题同样会随版本漂移**:凡带 arXiv id 的条目,标题以 `/abs` 页**当前**显示的 `citation_title`(最新版本)为准,不能用抓取候选清单时快照到的标题(实测两例:后续版本改换了标题核心动词/加了限定词,沿用旧标题=在 bib 里留一个作者本人已废弃的标题)。
- **venue 尚未正式出版时要留痕**:若候选的会议/期刊 proceedings 未发布、Anthology/DBLP 未收录,精确 venue 信息(如主会 vs Findings)只能靠作者本人确认——此时必须在交付材料里明确标注"venue 由作者确认,非从官方源核实,正式出版后应复核",不能当作与 Anthology 条目同等确定性的信息处理(实测:一条候选按搜索间接信息推断为主会,作者核实后实为 Findings)。
- 同一人名的变体(英文名 vs 真名、缩写 vs 全名)全 bib 统一——**问用户**,别猜;批量替换前先 grep 有没有第三方作者恰好同名(如真名带 "Van" 的别人)。**若官方索引之间(Anthology/OpenReview/DBLP/期刊页)对同一人的署名记录本身就不一致,或某一形式与另一位真实作者重名,以论文作者本人的确认为准(而非任一官方索引)**,并在交付材料里注明冲突及来源——它影响被引用者本人的引用记录归属(实测:四个官方源一致记作 A 形式,论文 PDF/arXiv/机构邮箱都指向 B 形式,且按 B 形式检索 Anthology 命中的是另一个真人——字面匹配会张冠李戴)。
- **作者归属统计口径**:任何"某学者被引用了几篇"的统计,必须基于每篇文章的**完整真实作者列表**(本 Phase 核实所得),而不是基于该文献是否出现在其 Scholar Profile 里——后者可能因未认领、消歧失败而不完整,会系统性低估某些合作者,尤其是论文产出量大、未逐一认领条目的资深研究者(实测:同一批候选,两种口径给某 PI 的篇数是 1 vs 8,差 8 倍,且恰好是最容易被误判为"贡献少"的那位)。
- 外部引用审计单(若有)照单执行,但**每条先独立查证再动手**;审计单里的"禁改边界表"(看着像错、实际忠实于官方记录的条目)一个都不碰。

### Phase 6 — 审阅与转正
- 项目若有颜色审阅流程:**所有新增/改动文字用审阅色**,交用户 PDF 审;已知坑:hyperref 的 `citecolor` 会盖掉引用键上的颜色,**纯加键的位置在 PDF 里看不出来**——在给用户的审阅清单里逐处列明。
- 编译验收(每次 push 前全套):0 新增 error、0 undefined、PDF 搜 `[?]`=0、书目条数=预期精确值、正文页数红线不破、**渲染出来的页要真的读一遍**(渲染能暴露源码审查看不见的问题)。
- 用户批准 → 转正(strip 颜色后重跑全部验收 + `.aux` 计数器核对)。

## 事故档案(前人踩过的坑,执行时逐条自查)

1. **层级吞并**:新 `\subsection` 插错位把后续 `\subsubsection` 吃成下级。
2. **块切除越界**:用"下一个结构命令"当块尾界会连带删掉中间的表格——**用块自己的末行锚定 + 断言跨度上限**;undefined-ref 计数是抓这类事故的最后防线。
3. **注释双胞胎**:文档里常有与 live 构件同名的注释残稿(同名 label、同串 `\citep`),任何查找/替换**先过滤注释行**并断言恰好 1 处 live 命中。
4. **消息交叉执行旧单**:多 agent 协作时,修订单可能晚于执行到达——写作 agent 落地前要确认自己拿的是**最新版**指令;lead 发现执行了旧单立即下返工令。
5. **作者数不全**:Scholar/搜索页折叠作者列表,漏掉通讯作者且不带 `and others` 是实锤错误——以 arXiv/anthology 全表为准。
6. **同组集中自引的观感**:审稿人对"附录集中自引"敏感。锚点稀释 + 真窄家能压住,但最终"留多少"是**作者的编辑判断**——把这个风险明确告知用户,由用户拍板。
