# 参考文献幻觉核查

> **一句话**：幻觉引用有两种。一种是**文献不存在**（维度 1–6 能抓）；另一种是
> **文献真实、但它并不支持你说它支持的事**（只有维度 7 能抓）。两种都要查——
> 实战中后者反而更常见、更难发现、也更容易被审稿人抓住。

## 何时用

- 投稿前 / camera-ready 定稿前自查
- 论文里有 LLM 协助撰写的段落（幻觉引用高发区）
- 合作者新增了一批引用，需要确认没引入错误
- 审阅他人稿件

## 0. 开工前先问清楚

1. **要交什么？** 只交 PDF → 优先级按"PDF 里看得见"排序；要交 LaTeX 源 → bib 冗余项也值得清。
2. **有 LaTeX 包吗？** 有就一定走 LaTeX 路径（见下）。
3. **是首审还是复审？** 复审只需审**新增/改动**的条目 + 验收上轮清单（用 `--keys`）。

---

## 1. Stage 0 —— 确定性检查（不联网，先做，很快）

> `<skill目录>` = 调用本 skill 时 harness 给出的 "Base directory for this skill"。

```bash
python3 <skill目录>/scripts/stage0.py <LaTeX项目目录> -o ./cite_out \
        --pdf <已编译.pdf> --year 2026
```

它做四件事并写出 `refs.json` / `stage0.json` / `contexts.json`：

1. **锁定编译链** —— 主 `.tex` → `\input` 链，**剥离 `%` 注释**后统计。
   ⚠️ 发现**多个候选主文件**时它会**拒绝猜测并退出**，让你用 `--main` 指定。
   投稿包里常同时有模板原版和真正编译的那个（如 `tmlr.tex` vs `tmlr_new.tex`），**选错会审错整份文献表**。
2. **解析 .bib** 为结构化条目。
3. **维度 8 重复检测** —— 归一化标题 / arXiv id / DOI 分桶 + 模糊标题比对。
   区分「两个 key 都被引 → **PDF 里真重复**（必修）」和「只一个被引 → 仅 bib 冗余（只交 PDF 可忽略）」。
4. **确定性红旗** —— 占位符（`YYYY`/`tbd`/`XXXX`）、arXiv-id 与 year 矛盾、未来年份、可疑 et al.

**光这一步就能零联网白捡**：`[?]` 未定义引用、重复引用、模板占位符、年份自相矛盾。

> 只有 PDF 没有 LaTeX 时：`pdftotext -layout` 提取 References 段，逐条切分后当 raw string 送下一步。
> **但要知道这条路更弱**——拿不到干净的"论点↔引用"映射，维度 7 受限，且 stage-1 更宽松（见
> `reference/pitfalls.md` B1）。

## 2. 逐条核查的 8 个维度

| # | 维度 | 查什么 | 失败 → 问题类型 |
|---|---|---|---|
| 1 | **存在性** | 这篇文献真的存在吗？能否解析到唯一真实记录 | `existence`（虚构） |
| 2 | **标题** | 标题是否与真实记录一致（忽略大小写/标点） | `title` |
| 3 | **作者** | 作者集合/首作者/拼写/**人数**是否对得上 | `author` |
| 4 | **年份** | 年份是否正确（预印本→正式发表的漂移算 minor） | `year` |
| 5 | **venue** | 期刊/会议是否属实；**声称已录用的必须去论文集实证** | `venue` |
| 6 | **DOI/定位符** | 给出的 DOI/URL 是否指向**这一条**记录 | `detail` |
| 7 | **内容一致性** | 正文声称它支持的论点，它是否真的支持 | `content`（最难查） |
| 8 | **重复条目** | 同一篇是否被定义成两个 key（独立一步，必做） | `duplicate` |

横切：**撤稿/撤回**（retracted）。

**判定 rollup**
- `REAL` —— 维度 1–5 全过（6 仅 minor）。**必须附可点击 canonical id。**
- `SUSPICIOUS` —— 单字段不符、venue 未证实、或证据太薄。
- `FABRICATED` —— 维度 1 失败，或 2/3/5 严重张冠李戴。**必须附检索轨迹**证明这个"否定"成立。
- **宁可标可疑，不轻易下虚假。**

## 3. Stage 1–2 —— 联网核查 + 对抗验证（Workflow 扇出）

```bash
python3 <skill目录>/scripts/make_workflow.py ./cite_out -o ./cite_out/run.js \
        --context "本文提出 X 方法，研究 Y 问题"      # 让 dim7 判断更准
# 复审只审新增/改动的：  --keys keyA,keyB,keyC
# 只有 .bib 没正文：     --no-dim7
```

然后 `Workflow({scriptPath: "<绝对路径>/run.js"})`。

流水线：`Verify(dims1-6, sonnet)` → `Adversary(**每条**都强制独立复核, opus)` → `Dim7(内容一致性)`。

### 🔴 强制流程：先报工作量 → 再报成本 → 给出建议 → 等用户拍板

**跑 Stage 0 之后、启动 Workflow 之前，必须先给用户这三样，然后停下来等确认。**
`make_workflow.py` 会打印前两样，第三样（建议）由你结合下表给。

#### 三个档位（`--level`）

| 档位 | agent/条 | 查什么 | 抓得到 | 抓不到 |
|---|---|---|---|---|
| `quick` | ≈1 | 维度 1–6，只对可疑项复核 | **编造的文献**、明显字段错 | 藏在 REAL 里的字段错、内容错配 |
| `standard` | ≈2 | + **每条**强制对抗复核 | 上面 + 作者/年份/venue 细错 | 内容错配 |
| `full` | ≈3 | + 维度 7 内容一致性 | 全部（含"文献真但不支持该论点"） | — |

> 成本估算按实测标定：**≈1.5–3.0 万 token/agent**（4 组真实运行反验通过）。

#### 建议怎么给（两根**独立**的轴，别混为一谈）

**轴 1 — 核查深度**（决定花多少钱）：

| 情形 | 建议档位 |
|---|---|
| **camera-ready / 投稿定稿前** | `full` —— 内容错配是审稿人最容易抓的，别省这一步 |
| 有 LLM 协助撰写的段落 | `full` |
| 只有 `.bib` 没正文 | `standard`（维度 7 做不了） |
| 早期草稿、还会大改 | `quick` |
| 条目 >150 且预算紧 | `quick` 全量 + 对可疑项单独 `full` |
| 复审（作者刚改完） | 任意档位 + `--keys` 只审新增/改动的 |

**轴 2 — 主循环 effort**（几乎不花钱，但决定判断质量）：

- 子 agent 的 model/effort 在脚本里钉死，**与会话 effort 无关**。
- 会话 effort 影响的是**你**：挖 field_diffs、独立复核、辨别误报（§4）。
  **误报的代价最高**——会让作者去"修正"本来正确的地方。
- **一律建议 effort ≥ high**；ultracode 不是必需（skill 调用本身已是 Workflow 的合法 opt-in）。
- 所以性价比最高的组合常常是：**便宜档位 + 高 effort**，而不是"要么全开要么全省"。

#### 报给用户的话术模板

```
Stage 0 已完成（零成本），发现：<undefined/重复/占位符/年份矛盾 的实际结果>

联网核查的工作量与成本：
  quick    ≈ N 个 agent，≈ X–Y 万 token —— 只保证抓出编造的文献
  standard ≈ 2N,          ≈ ...        —— 加每条对抗复核
  full     ≈ 3N,          ≈ ...        —— 加内容一致性（唯一能抓"文献真但不支持该论点"）

建议：<档位> + effort ≥ high，理由是 <camera-ready / 只有 bib / 预算紧 ...>
要开始吗？
```

### 为什么必须扇出（不是可选加速）

每条引用都要查好几个源，串行做会在跑完前撑爆主 agent 的 context。扇出让每个 sub-agent
烧自己的 context、只交回结论——所以本 skill 必然是几十到几百个 agent。

**实测开销**（估算公式据此标定）：

| 规模 | agent 数 | tokens |
|---|---|---|
| 251 条全量（含对抗） | 349 | 626 万 |
| 44 条 dims1-6（含对抗） | 90 | 263 万 |
| 44 条维度 7 | 47 | 132 万 |
| 23 条复审（含对抗+dim7） | 74 | 213 万 |

**默认 workflow 大小指引是 15 个 agent**，本 skill 动辄百倍于此——所以上面那套「先报量、再报价、
给建议、等拍板」是**强制的**，不是客气。

**缩小规模的正当做法**：
- 复审时 `--keys` 只审新增/改动的条目（**最有效**，通常砍掉 80%）
- 降档到 `--level quick` / `standard`
- 条目极多（>150）分批跑
- 预算很紧：**先只跑 Stage 0**（零成本，就能抓出 `[?]`／重复／占位符／年份矛盾），再决定要不要联网

> **为什么每条都要对抗复核**：大规模 sweep 会把字段小错记成「REAL + field_diff」而不是 SUSPICIOUS，
> 于是跳过复核 → 漏检。规模不大时（≲100 条）一律全量复核，别只抽样。
>
> **为什么数据内嵌进脚本**：Workflow 的 `args` 传大 JSON 不可靠（几十 KB 会变成空/字符串）。
> `make_workflow.py` 直接把数组写进脚本，最稳。

## 4. ⚠️ 读结果的纪律（最容易在这里前功尽弃）

**绝不能只看 `flagged_*` 和汇总标签。** 必做三件事：

1. **对全部条目（含 REAL）导出 `field_diffs`**，按 author/year 类优先排序，逐条人工过。
   实战中最严重的错常常藏在标 REAL 的条目里。
2. **单独看 `author_truncated`** —— 作者表被截断却没写 `and others`，书目会谎称这篇就那几位。
3. **单独看 `venue_not_confirmed`** —— 真实论文 + 未证实的"已录用"声明 = 真问题。

然后**对每个准备上报的结论亲自复核一遍**（直连 arXiv / ACL Anthology / OpenReview / HF API）。
sub-agent 自己也会幻觉；上报前要能说出"canonical 记录写的是 X，bib 写的是 Y"。

**下判断前请读 `reference/pitfalls.md`** —— 那里列了会导致误报的 8 类情形（忠实于官方记录的
"假拼写错误"、同一人的不同名字写法、TMLR 的 OpenAlex 索引缺失、403 ≠ 失效……）和会导致漏检的
10 类情形（逐项断言、注释里的原意、自引、混源作者表……）。**误报和漏检同样致命。**

## 5. 维度 7 单独说明（价值最高的一维）

被引文献可以 100% 真实、字段 100% 正确，**错的是它被挂到了哪个论点上**。维度 1–6 按定义看不见。

- **类别指针**（`MoE architectures~\citep{a,b,c}`）→ 属于该类别即 SUPPORTED，别苛求精确对应。
- **逐项断言**（`has been adopted by several recent systems~\citep{A,B,C,D}`）→ **逐个 key 检验**。
  这是错配的高发区，因为正文往往**不点名**，作者自己也看不出 key 挂错。
- **属性词**（lossless / training-free / zero-shot / first to）和**具体数字**最需要抠。
- ⭐ **去读被注释掉的原稿行**：旧版句子里常明写着作者当时想指谁，一眼看出 key 挂错了。

## 6. 产出（按读者分开写，别只出一份）

| 文件 | 读者 | 内容 |
|---|---|---|
| `citation_audit_<paper>.md` | **作者**（做决策） | 结论速览、证据、为什么、可选项、需要作者拍板的地方 |
| `citation_fixes_<paper>.bib` | 作者/执行方 | 可直接替换的修正条目 |
| `citation_fix_WORKORDER.md` | **执行方**（动手改） | 逐字 old→new + file:line、⛔不许改清单、验收清单 |

**施工单必须包含的三样**（缺一就会出事）：

1. **⛔ 不许改清单** —— 把所有"看着像错但其实正确"的项显式列出来。
   否则执行方会顺手"修正"它们，**反而制造错误**。
2. **逐字 old→new，且锚点唯一**。给之前先验证：
   ```bash
   grep -c -F "<old_string>" <file>     # 必须 == 1
   ```
   不唯一就换更长的锚点（例如把上一行一起带上）。真实案例：`year={2021}` 在 bib 里出现 4 次，
   全局替换会改坏另外 3 条。
3. **验收清单** —— 重新编译、PDF 搜 `[?]`=0、书目条目数、**在渲染出的 PDF 里 grep 新值确认生效**、
   `git diff` 逐行复核。

需要作者拍板的地方（例如"你本意指的是 Gemini 还是 Gemma 4"）要**显式标注"先确认再动手"**，
不要让执行方替作者做学术判断。

---

## 7. 复审（作者改完之后）

1. 与上一版做**全量 diff**（bib + 所有 `.tex`）——确认改动是外科手术式的，没有附带损伤。
2. 逐项验收上轮清单（改好了 / 没改 / 改错了）。
3. 只对**新增或改动**的条目跑 workflow（`--keys`），别重跑全部。
4. **确认 PDF 重新编译过**：在渲染书目里直接 grep 新值。
5. 回归检查：`[?]`=0、重复=0、引用总数是否符合预期。
6. **如果上一轮的某条结论被证明是错的，明确撤回并说明原因**——比默默改口重要得多。
